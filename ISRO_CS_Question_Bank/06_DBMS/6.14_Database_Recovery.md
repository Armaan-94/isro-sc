# 6.14 Database Recovery

**Notes:** [14 Database Recovery](../../DBMS_ISRO_Notes/14_Database_Recovery.md)

> 22 questions.

---

**Q1.** ARIES phase order:
(a) redo, undo, analysis (b) analysis, undo, redo (c) analysis, redo, undo (d) undo, analysis, redo
**Answer: (c).**

**Q2.** Write-ahead logging requires:
(a) data before log (b) the log record on stable storage before the data page is written (c) only commits logged (d) checkpoints instead
**Answer: (b).**

**Q3.** Deferred update never needs UNDO because:
(a) no logging (b) the database isn't modified until commit (c) checkpoints (d) CLRs
**Answer: (b).**

**Q4.** Immediate update; log has <Ti start> but no <Ti commit> at crash:
(a) redo (b) undo (c) nothing (d) redo then undo
**Answer: (b).**

**Q5.** Main advantage of shadow paging:
(a) concurrency (b) no log; recovery is near-instant (c) less space (d) no garbage collection
**Answer: (b).**

**Q6.** ARIES redoes actions of transactions that will be undone because:
(a) bug (b) "repeating history" keeps redo simple; undo cleans up (c) undo needs it (d) CLRs need it
**Answer: (b).**

**Q7.** PageLSN prevents:
(a) duplicate logs (b) redoing an update already on the page (c) undoing commits (d) checkpoint corruption
**Answer: (b).**

**Q8.** Steal + no-force needs:
(a) neither (b) redo only (c) undo only (d) both undo and redo
**Answer: (d).**

**Q9.** A compensation log record (CLR) is:
(a) undone later (b) redo-only; records an undo action (c) a duplicate (d) for analysis only
**Answer: (b).**

**Q10.** No-steal + force needs:
(a) undo and redo (b) neither (c) undo only (d) redo only
**Answer: (b).** Uncommitted data never reaches disk; committed data always does.

**Q11.** Steal + force needs:
(a) undo only (b) redo only (c) both (d) neither
**Answer: (a).**

**Q12.** No-steal + no-force needs:
(a) undo only (b) redo only (c) both (d) neither
**Answer: (b).**

**Q13.** Log: <T1 start>, <T1 commit>, <checkpoint>, <T2 start>, <T3 start>, <T2 commit>, crash. Immediate update. Actions?
(a) redo T1, T2; undo T3 (b) redo T2, undo T3; nothing for T1 (c) undo all (d) redo all
**Answer: (b).** T1 committed before the checkpoint, so its updates are already on disk.

**Q14.** Under deferred update with the same log, what happens to T3?
(a) undo (b) redo (c) nothing: its updates never reached the database (d) restart automatically
**Answer: (c).**

**Q15.** Recovery operations must be:
(a) idempotent (b) commutative (c) random (d) single-use
**Answer: (a).** Redoing twice must equal redoing once.

**Q16.** A checkpoint mainly:
(a) limits how much of the log must be scanned after a crash (b) commits all transactions (c) deletes the log (d) locks the database
**Answer: (a).**

**Q17.** An update log record stores:
(a) transaction id, item, old value and new value (b) only the new value (c) only the transaction id (d) the whole database
**Answer: (a).** Old for undo, new for redo.

**Q18.** Stable storage is:
(a) RAM (b) an idealised storage that survives all failures, approximated by replication (c) cache (d) a single disk
**Answer: (b).**

**Q19.** The ARIES analysis pass scans:
(a) backward from the end (b) forward from the last checkpoint (c) only the dirty page table (d) the data pages
**Answer: (b).** Undo scans backward.

**Q20.** "Loser" transactions in ARIES are:
(a) active (uncommitted) at the crash and must be undone (b) committed ones (c) aborted before the checkpoint (d) read-only ones
**Answer: (a).**

**Q21.** Durability is provided mainly by:
(a) logging and the recovery manager (b) locking (c) indexing (d) normalisation
**Answer: (a).**

**Q22.** Real DBMSs mostly use:
(a) shadow paging (b) log-based recovery (WAL / ARIES) (c) no recovery (d) manual backups only
**Answer: (b).**
